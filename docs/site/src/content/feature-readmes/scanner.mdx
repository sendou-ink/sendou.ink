Browser app (route `/scanner`, linked from the Tools menu) that watches a
capture card or OBS Virtual Camera while you play, or scans VoD files,
detects Splatoon 3 UI screens with OpenCV.js in a Web Worker, and parses them
into events speaking sendou.ink ids (`ModeShort`/`StageId`/weapon ids/`Ability`).
Events aggregate client-side into `ScannerMatch` objects
(`core/scanner-match.ts`) — one detected game per object, every field
nullable — which feed `/ingest` (features/scanner-ingest, live captures only), the `/vods/new`
prefill, the match cards and the clip cutter. Imported from the emberz repo;
see `MIGRATION.md` there.

Deliberate convention exceptions (ported wholesale): the UI is English-only
(no i18next; the public release should flip that), `tests/node-test-compat.ts`
uses a default export to stay a `node:test` drop-in, and the suites assert
with `node:assert/strict` rather than the repo-wide `expect`. Keep whichever
file you touch on the idiom it already uses — a half-migration would leave
three idioms behind.

## Product shape

Anyone can capture, scan files and get clips locally; only uploading needs a
login (`components/upload.ts` mirrors the root loader's user for the
controllers). The landing (`components/LandingView.tsx`) is a title and a
"How it works" disclosure (requirements, what's read, privacy, what's
uploaded — keep it in sync with `UPLOADED_LOBBIES`), two entry cards
(Live / File), the clip history strip and the sessions list; everything else
is one component, `components/SessionView.tsx`, rendered identically for the
running capture (`LiveView`), a past session (`PastSessionView`) and a
scanned VoD (`VodView`): header, clip strip, then match cards
(`components/MatchCard.tsx`) newest first. Views are picked by the `view`
search param (`scanner-search-params.ts`: `live`, `session&id=`,
`vod&name=`, `coach&name=` (a scanned file's coach events beside its video), `clips`, `debug` and the dev-only `fixtures` and `montage`). Nothing links to
the `debug` screenshot view: dropping an image on the landing's File card
opens it, for anyone, through the same handoff Inspect uses.

- **Controllers are module singletons**, not view state: the capture
  (`components/live-session.ts`) and a running VoD scan
  (`components/vod-scan.ts`) are mounted above the view switch, so moving
  between views never stops them; a capture runs until Stop (even off the
  page), a scan until it finishes or the scanner page is left.
  Views subscribe through `useSyncExternalStore` hooks, as they do to the
  event feed (`components/events-feed.ts`, sessions built once per refresh),
  the clip list (`clips-feed.ts`), the VoD list (`vods-feed.ts`) and the
  localStorage settings (`settings.ts`: source, upload toggle, clip toggle).
- **Header button** (`components/ScannerActivity.tsx`): the site header
  shows the capture while it runs or failed, and idle (start from any page)
  once this browser has captured before; idle is left out on mobile. The
  header imports only `scanner-activity.ts`, which holds nothing but the
  capture status `live-session.ts` publishes on transitions, so browsing
  without a capture loads no scanner code and a running one never
  re-renders the header per frame. The popover's content
  (`ScannerActivityLive.tsx`, the live preview included) is lazy and mounts
  only while open; starting from there sets the upload user and settles the
  clip store as the scanner page does.
- **Sessions** are client-only and derived at render (`core/sessions.ts`):
  live events ordered by `detectedAt`, split wherever a gap of ≥ 2 h opens,
  keyed by the first event's `detectedAt` (the URL id). A VoD is its own
  session keyed by file name. Live `t` is wall-clock seconds (`Date.now()`)
  so events from different page loads share one timeline; the ring buffer
  stamps footage the same way.
- **Retention** (`store/events.ts`, on a throttled pass at every save):
  whole sessions older than 30 days, beyond the newest 20 or past the
  `MAX_STORED_EVENTS` budget (~140 SZ games; the newest session is never
  cut) go — never part of one, so a kept session's cards always expand to
  their full timeline and scoreboards. A saved event re-reads only what was
  saved since the last read (plus the events a send status write named),
  and a match whose events are unchanged objects is reused rather than
  rebuilt (`MatchBuildCache`); live sends take their matches from the feed.
  So neither the store's size nor a long session costs much per saved event.
- **Event versions** (`core/event-version.ts`): stored events outlive the
  code that wrote them and are rebuilt into matches by whatever is deployed
  now, so every record (`events`, `vod-events`, a compacted game's sources,
  a Game data zip's `events.json`, a tape's header) carries the version `v`
  its `type`/`data`/`scores` were written at; a record without one is version 1
  (version 2 replaced a read's one `confidence` with `scores` per field; an
  older read is brought up with its confidence as the one score of the whole
  read, under `*`; version 3 replaced a PlayerStatus read's special/dead
  flags with per-slot evidence, an older read's flagged state counting as
  one confident read of it). The
  store reads (`listEvents`, `getEvents`, `loadVodEvents`,
  `listCompactedMatches`) and the tape loader hand back
  `EventVersion.readable` events: older ones run through the upgrade steps
  in memory (nothing is rewritten in the store), ones a step drops or that
  newer code wrote (another tab after a deploy) are left out and stay
  stored until retention takes them. **Changing an event's shape so that a
  reader of the old shape breaks (renamed, removed or retyped field, renamed
  type) means bumping `CURRENT` and adding the step from the previous
  version**; an added optional field needs neither, and IndexedDB's
  `DB_VERSION` is only for the stores themselves. A compacted game's `match`
  is frozen as built and not upgraded.
- **Compaction** (`events-feed.ts` on refresh, `store/compacted-matches.ts`):
  72 h after a session ends its games are frozen as built, one record each,
  keeping every source event except the per-second Objective/PlayerStatus/
  StripWeapons reads (`compactSources`; ~85% of a game's events, ~6× its
  bytes), and its raw events are deleted in the same transaction. Cards,
  uploads (`sendCompacted`) and the game data zip read a compacted session like
  a raw one, but it no longer picks up match builder fixes and its
  `Raw detections` CSV option is disabled. Compacted sessions share the
  30-day / 20-session retention with the raw ones. Every listed event keeps
  its full-res analyzed frame as a lossless WebP (~1.1 MB at 1080p, half a
  PNG; the montage's VoD scans skip it with `attachFrames: false`), live and
  VoD frames alike bounded by 72 h and a shared 500 MB budget, newest first
  (`store/frames.ts`), the event staying with `hasFrame: false`. A VoD scan
  also keeps every frame of each map open from its first kept minimap read
  on, downscaled to 960 px lossy WebP (`vod-minimaps`, `snapshotMinimaps`),
  for coach mode's "map as last opened"; those live as long as the VoD and
  are not trimmed. Clips have
  their own cap and outlive session deletion.
- **Upload** is on by default when logged in (settings toggle, persisted).
  Live: a scoreboard closes its match and sends it, a 15 s tick retries
  unlinked matches on a backoff (`sendou-ingest.ts`) and flushes closed
  matches whose send was skipped; Stop sends what is left. Server-side, a
  game report (tournament or SendouQ) links the stored, still unlinked
  matches hinted to its context (`scanner-ingest/core/relink.server.ts`),
  and a SendouQ report undo drops the map's links (a tournament undo deletes
  the result, cascading them), so a correction relinks without a resend.
  `/ingest` refuses (429) a sender past their quota (stored matches per
  hour, stored size per day), a game links at most one read per sender, and
  a daily routine deletes linkable reads still unlinked after 30 days.
  Per-event send
  statuses back the cards' upload status button (`UploadStatus.tsx`) and its
  Retry/Upload. VoD scans never upload: their reads carry no wall clock, and
  without one a stranger's game can't be told apart from the uploader's
  (linking needs a `playedAt` within 30 min of the game's report).
- **CSV** is a normal feature: `⇩ CSV` in every session header offers
  `Matches` (`core/csv/matches.ts`, one row per game, the rows the cards
  render) and `Raw detections` (`core/csv/events.ts`, one row per event).
  Column names stay English keys.
- **Game data** (`components/match-zip.ts`): an expanded match card's
  download, what users report a misread with — `match.json` (the card's
  match plus its clips' kills and stream/file `start`/`end`), `events.json` (every source event, each naming its frame folder)
  and `frames/<n>-<type>-<position>/` with the frame plus a prefilled
  `expected.json`, fixture-ready. A VoD's game also holds `scan-log.json`,
  the whole scan's log: with the video file the scan can be run again as it
  ran (see "Scan log and replay").
- **Debug gate** (`use-debug.ts`: DEV/ADMIN role or `?debug=true`, which
  Settings → Debug → `Enable debug` sets):
  `Save frame as fixture` (Settings → Debug, live only) and
  `?telemetry=true`. The screenshot view (`ScreenshotPage.tsx`) is not
  gated (drop a frame from a game data zip on the landing to inspect it);
  the fixtures and montage views are dev-only.

## Clips

Clips are real video with audio, cut in the browser. `core/clips/scoring.ts`
is the pure, swappable scorer: only the POV player's own kills feed it
(`ScannerMatch.kills`, off the kill feed); a streak is consecutive kills with
no POV death between them and no pause over `STREAK_MAX_GAP_S`, cut where the
clip would outgrow `MAX_CLIP_SECONDS`; `MIN_KILLS` (4) makes it a window,
scored `kills² + kills / span`. Both controllers run windows → cut →
`store/clips.ts` over the
session's matches plus the stretches no scoreboard or minimap backs
(`buildScannerMatches(…, { unbacked: true })`, `LiveSession.clipMatches`):
a streak must not wait for a results screen that may never be read, and live
the ring would have dropped it by then:

- One capture per browser profile: `startCapture` holds a Web Lock
  (`CAPTURE_LOCK`) for its lifetime, so a second tab gets an error instead
  of a second pipeline writing every game twice (two samplers on one store
  double each event, and the repeated scoreboard opens a duplicate match).
- **Live** (`capture/ring-buffer.ts` + `ring-buffer.worker.ts`): the
  stream's tracks become `MediaStreamTrackProcessor` streams, transferred to
  a worker so a busy page never costs the footage a frame (on the main
  thread ~12% of a 60 fps track was lost to the one-frame processor
  buffer). There the video runs through a `VideoEncoder` (H.264, keyframe
  every 2 s, bitrate scaled by pixel rate: ~12.5 Mbps at 1080p60) into a ring
  of GOPs holding the last
  `RING_BUFFER_SECONDS`; the audio through an `AudioEncoder` (AAC, else
  Opus) into the same ring. `openCapture` asks for 60 fps explicitly, as
  Chromium's default of 30 would halve a capture card. Packets carry the
  wall-clock time their frame was captured (noted at encoder input, claimed
  at output, so encoder latency never shifts audio against video): video by
  frame timestamp, audio by sample position (`SampleClock`), because audio
  timestamps drift against the sample count on some sources (a display
  capture, an element's `captureStream`) while the AAC encoder counts
  samples — matching by timestamp pushed later packets into the future and
  a cut lost its second half of audio. In the MP4 the audio runs on by
  sample count from its first packet and only jumps forward on a delivery
  gap over `AUDIO_RESYNC_S`. The remaining constant offset between a
  capture card's picture and another path's sound (desktop audio, a
  loopback device) is the `audioOffsetMs` setting, applied at cut time.
  The audio input is watched for signal: a device that opens but sends
  silence, and an encoder that gives up, show on the live status line. A window is cut once `windowClosed` (no
  kill can join and the
  tail is captured): the GOP at or before its start through its end, muxed
  to MP4 with mediabunny's `EncodedVideoPacketSource` — no decode; a ring
  that only begins more than `MAX_MISSING_LEAD_S` after the asked start
  (a capture restarted mid-streak) yields nothing rather than a clip
  missing its kills. A kill belongs to one clip: a window over footage
  already cut — redrawn by a late-read kill, or seen again because the
  session outlived the capture that first cut it — is skipped unless it
  scores higher, when it is cut and the clips it overlaps are deleted
  (`cuts` plus the session's saved clips, `live-session.ts`). What
  the clips hear is the `audioSource` setting: the source's own input
  (`audioInputFor`: same `groupId`, else a shared label prefix; OBS Virtual
  Camera carries none), the desktop's sound (`openDesktopAudio`: the share
  picker's audio track, opened before the camera so the click's activation
  still covers it, its video surface dropped), any audio input, or off.
- **VoD** (`capture/vod-clips.ts`): packets from the keyframe at or before
  the window start are copied into a fresh MP4 (video + audio, no
  re-encode, so a minute of 1080p takes well under a second). mediabunny's
  `Conversion` with `trim` always transcodes; keep using the packet copy.
  A file's windows come from the clip criteria picked under its header
  (`VodClipsPanel`, `criteriaWindows` in `core/clips/criteria.ts`: min
  splats and a length cap per splat count, kept in localStorage, the
  defaults reading like the live scorer's 4 splats within a minute) rather
  than the live `clipMinKills` setting, and live outside the scan
  (`components/vod-clip-cutter.ts`): a criteria change re-reads the saved
  scan, keeps the clips whose run of kills is still wanted (keyed by last
  kill and count), deletes the rest and cuts the missing ones, the best
  `MAX_VOD_CLIPS` (20) of them. A scan from an earlier visit kept no clips,
  so the panel asks for its file to cut them.
- **Encoder**: hardware first, then software — Chromium's
  `prefer-hardware` never falls back by itself (Linux, VMs, older GPUs). A
  hardware encoder can also fail only once frames flow (NVENC sessions taken
  by OBS): the worker swaps in software and restarts the ring. If nothing is
  left the status line shows clips as failed; the ring still cuts what it
  holds.
- **Buckets** (`store/clips.ts`): `session` holds the running session's
  clips (kept until Stop, budget permitting); Stop rolls them into `history`,
  where `MAX_HISTORY_CLIPS` (20) applies by score — download to keep. A
  file's clips (`vod`) live for one visit and are purged on the next page
  load; the file is on disk. Bytes are capped too: the live clips (session
  and history together) stay under `LIVE_CLIPS_MAX_BYTES` (4 GB) and each
  file's clips under `VOD_CLIPS_MAX_BYTES` (2 GB, they keep the source
  bitrate), lowest score dropped first, and a clip that
  would eat into the last 250 MB of quota (the events share it) is not
  saved — on a file the scan carries on with the next window. Clip records carry the real `start`/`end`
  seconds (a packet-copied clip starts at a keyframe), and a card's deaths
  and kills get a ▶ when a clip covers their `t`.
- **Trim** (`capture/clip-trim.ts`, `ClipTrimBar`): the clip dialog's
  Trim (or a history card's scissors) swaps the video's controls for a
  macOS Preview style bar — a filmstrip of keyframes, a yellow frame whose
  handles set the range, playback that stops at its end — and downloads
  the range. mediabunny's `Conversion` copies packets from the keyframe
  before the start and writes an MP4 edit list hiding the lead-in, so the
  cut is frame accurate with no re-encode. The stored clip is untouched.
- **Mute music** (the clip dialog's switch, also in the trim bar;
  `capture/clip-music.ts` and its worker, `core/music/`): the battle track is subtracted from the clip's
  sound, the other game sounds kept, and the clip is written again (video
  copied, sound re-encoded) for playback and download. Landmark
  fingerprints (`fingerprint.ts`: paired spectrogram peaks, votes per
  (track, offset)) name the track and the few places in it that sound
  alike (a song repeats itself); each is aligned to a fraction of a sample
  by phase-transform cross-correlation, with the drift between capture and
  console clocks, and every second goes to the one that explains the clip
  best — fingerprint votes alone thin out under game sounds and casters,
  leaving the start and end of a clip untouched, and cannot tell a verse
  from its repeat. The track, resampled onto the clip's timeline, comes out
  through a per-bin gain fitted to the clip in the short-time Fourier
  domain (the game ducks and filters the music, e.g. while splatted), plus
  a Wiener post-filter (`music-removal.ts`). A 60 s clip takes a few
  seconds. The music set lives on the CDN at `scanner/v1/bgm/`: `index.bin`
  (fingerprints and the track list, ~1 MB) and the tracks themselves,
  fetched only when matched. `pnpm scanner:build-music-index <folder>`
  builds it from a folder of Opus tracks (titles from the file names, ids
  slugs of the titles); `pnpm scanner:remove-music <video>`
  runs the same removal in Node and writes before/after WAVs for listening.
  Music missing from the set (lobby, results, a streamer's own) is left
  alone. What is left of the music is mostly the reference's own mismatch:
  the YouTube rips differ from the game's playback (the rips' repeats of a
  passage already differ from each other by 8–11 dB), so a cleaner source
  (the game's own streams) would cancel deeper.
- **Remove music from a whole VoD** (the VoD view's Remove music;
  `capture/vod-music.ts` and its worker, `core/music/music-stream.ts`): the
  file itself again, video packets copied bit for bit, the music-free sound
  as the first (default) audio track and the original audio tracks copied
  after it. Two passes so hours of sound never sit in memory: the search
  runs `findMusic` over 90 s windows overlapping by 20 s, each keeping the
  segments in its middle, and the subtraction decodes the sound again in
  30 s chunks with 3 s of margin either side (on the STFT's hop, so the
  output is the whole-sound subtraction to −50 dB); chunks no segment
  reaches pass through. Every track is muxed up to where the music-free
  sound has got, so the muxer holds seconds, written to a file picked in
  the save dialog, or without one (Firefox, Safari) to the origin private
  file system and downloaded from there; those copies are deleted on a
  page load an hour later (`deleteStaleVodMusicFiles`). The AAC encoder's
  priming (2112 samples in Chrome on macOS) isn't signalled by
  mediabunny's muxers, so `audioEncoderDelay` measures it by encoding a
  click and the new sound starts that far in; the clip mute does the
  same. A 33 min 1080p VoD takes about 25 s to search and 75 s to write in
  Node (`pnpm scanner:remove-music <video> --video`, the same passes with
  ffmpeg doing the decoding and muxing).

## Tournament montage (dev only, PoC)

`view=montage` (Settings → Debug → Tournament montage, development only)
builds the basis of a tournament highlight video. `pnpm vods:download <id>`
writes the match VoDs of the top 8 teams (`--all-teams` for every team) to
`scripts/output/vods/<id>/` together with `tournament.json` (name, start,
logo, top 8, every team that played, each VoD's POV team —
`MontageManifest` in `core/montage.ts`) and the logos it names; the view
opens that folder through the File System Access API's directory picker
(Chrome). `components/montage.ts` scans every VoD without games yet through
`startVodScan` (`clips: false`: saved like any file scan, so they also show
in the landing's list) and lists every streak meeting the criteria as a
candidate, best score first (`criteriaWindows`, shared with a VoD's clips): min splats (default 3) and
a length cap per splat count before fast-forwarding (defaults 2: 20 s,
3: 30 s, 4: 45 s, 5+: 60 s), picked on the page and kept in localStorage.
Candidates are grouped by the POV player's base weapon (read off the
game's scoreboard seat, variants folded to their base) and can be filtered
by team. Only top teams' candidates are listed: a POV VoD's under its team,
a cast's under either side (`candidateTeamIds`), and each pick is added
under one of them. The scanned games, the picks (stored whole, so changing
the criteria never drops one) and the folder's handle live in the
`montages` store (`store/montages.ts`, one record per tournament): a reload
restores the latest montage at once and reconnects the folder itself when
Chrome kept the permission, else `Reconnect folder` asks again.

Rendering (`capture/montage-render.ts`, overlays in `montage-overlays.ts`)
re-encodes everything at 1920×1080 60 fps: the intro card (the tournament
and every team's avatar), then the top 8 counting down to the winner
(`montageTeamSections`), each team's card (placement, roster and comp)
followed by its picks in order. The comp:
`montage-comps.ts` builds it the way the results image export does, from
the scans alone — every scoreboard names both sides' weapons and the POV
seat tells which side is the streamer's team, so a team needs VoDs of its
own or of its opponents to get one). The cards and each
clip's ribbon (round, both teams, the POV player and their profile link;
fades out after 5 s) are the image export's graphic blocks
(`features/img-export`), mounted off screen by `MontageGraphics.tsx` in the
dark theme and rasterized with snapdom at the scale that makes them full HD —
the renderer asks for them through `setMontageGraphicCapture`, so the page
must stay open. Each card is captured twice, with and without its revealed
items (the intro's team avatars, a team card's roster): the renderer draws
the empty one and brings the items in from the other (`REVEAL_TIMINGS` in
`montage-overlays.ts`), with a moving wave along the bottom. The page's
Cards panel shows each card live with the same animations (to tweak its
styles with hot reload; Replay restarts them) and downloads it as captured. The manifest carries what they show (round names, both
sides, the streamer, rosters, tier, organization, counts — no
weapons: those come from the scans) and the
download script saves every image it names next to the VoDs. Dead time
between two kills — from 3 s after one to 3 s before the next, when at
least 2 s — plays at 4×, muted and badged (`playbackSegments`). Each clip's
sound is normalized to -16 LUFS (`core/loudness.ts`: BS.1770 integrated
loudness, at most +24 dB) with a look-ahead limiter holding peaks under
-1 dBFS. An optional music (or video) file replaces the game sound for the
whole video: looped as needed, faded in and out, normalized the same way;
it is kept in the montage's record. Chrome's save dialog streams the MP4 to disk; without it the file
is built in memory and downloaded.

## Commands

```sh
pnpm test:scanner                       # golden-file suite over tests/fixtures/ (Vitest, Node)
pnpm test:unit:browser                  # includes tests/logic/ — the fixture-free half, see below
pnpm scanner:report                     # accuracy table + name character error rate across fixtures, then the threshold margins (--margins = those alone)
pnpm scanner:fixtures [name-substring]  # run detectors over matching fixtures, verbose
pnpm scanner:replay <dir> <startT> <fps> # replay ffmpeg-extracted frames through the scheduler+detectors
pnpm scanner:unpack-zip <zip> <new-dir> # validate + unpack a user's Game data zip (refuses anything matchZip doesn't write)
pnpm scanner:scan-vod <video>           # VoD scan as a CLI (ffmpeg): video in, events CSV out (--gpu, --record, see "WebGPU"; --tape, see "Event tapes")
pnpm scanner:scan-vod <video> --replay <scan-log.json> # the scan a browser ran on that file, run again from its log, see "Scan log and replay"
pnpm scanner:tape <name> "<description>" <zip>... # record an event tape from Game data zips
pnpm scanner:status-audit <events.csv | name.tape.jsonl>  # diff the decoded status vs scoreboard D/S, rank fixture candidates (a tape keeps the evidence the CSV loses)
pnpm scanner:bootstrap-atlas            # harvest labeled fixture crops into the glyph atlases
pnpm scanner:build-glyph-atlas          # add the font-rendered charset (fonts required, see below)
pnpm scanner:build-localized-entries    # regen localized closed sets from ../splat3
pnpm scanner:build-planner-signatures   # regen the minimap stage-ID atlas from the assets repo
pnpm scanner:build-music-index <folder> # regen the battle music set clips' "Mute music" subtracts
pnpm scanner:remove-music <video>       # take the music out of a video's sound, before/after WAVs
pnpm scanner:remove-music <video> --video # the whole video again without the music, original audio kept
pnpm scanner:gpu-parity                 # every fixture: OpenCV vs WebGPU parse decisions + GPU upscale pixels
pnpm scanner:gpu-replay <corpus-dir>    # replay recorded match requests on WebGPU, timed, exact-checked
```

Scanner scripts run through `vite-node -c scripts/scanner/vite-node.config.ts`:
the root vite config pre-bundles `@techstark/opencv-js` for the browser worker
and vite-node must not consume that prebundle. The package is pnpm-patched
(`patches/`) to wrap its thenable CJS export as `{ cvReadyPromise }`,
unwrapped in `core/cv.ts`, and to expose its heap's `WebAssembly.Memory` as
`cv.wasmMemory` (captured from its one `WebAssembly.instantiate` call, all
in the short wrapper lines: the minified runtime line is never touched, so
the patch stays small). `core/frame-kernels.ts` runs on that memory.

- `core/` is pure (mats in, events/matches out) and runs in the worker, the
  debug view, and Node tests. No DOM/browser APIs; Node-only helpers live
  in `node/`. Pure data/type imports from `~/modules` and
  `~/features/build-analyzer/data` are fine — valibot and the app config graph
  are not (schemas live in `scanner-schemas.ts`; core only `import type`s
  the shapes).
- `core/match-builder.ts` turns a timeline into `ScannerMatch`es: a MapStart
  opens a match, a scoreboard closes one (claiming the last 8 min of deaths
  when the intro was missed). A match needs a scoreboard, a personal results
  screen, a minimap or a minute of counter reads after its intro to be kept
  (the last for footage with neither, e.g. no results screen shown and the
  map never opened; it has no players, so it is not uploaded). Matchmade

  DetectorScheduler decides which detectors see a frame. Failing gates are
  re-checked every `searchIntervalS` (0.25s — produced VoDs cut screens to
  ~1s, and gates are ~ms-cheap); a passing gate drops to the dense refine
  cadence (`refineIntervalS` overrides for expensive parses). Suppression
  ends a refinement streak as soon as the read the timeline keeps of the

  on stagnation: `maxStagnantParses` parses that changed nothing the timeline

  complete read. A cast

  the gate. `checkIntervalS` hard-caps both phases; `attachFrame: false`

- VoD scans (`components/vod-scan.ts`): on the WebCodecs path each worker
  scans its own contiguous slice (no frames cross the main thread), with
  helper workers of its own that keep the waits off its thread: its slice
  decodes in `worker/decode.worker.ts` (mediabunny; the per-sample
  bookkeeping of a 60 fps slice cost the analyzer ~0.15 ms a sample), frames
  are read back in two `worker/readback.worker.ts` and the analyzed frames'
  images encoded in `worker/frame-encode.worker.ts` (a lossless 1080p WebP
  blocks its thread ~30 ms; the results still post in order). The analyzer
  takes every sample's step strictly in stream order — bookkeeping, analysis
  when due, the calm check — against the scheduler state the previous
  analysis left, so the analyzed frames are exactly those of a
  one-frame-at-a-time scan. Only the waits overlap: while a pass runs, the
  next samples are decoded and held, those before `nextDueLowerBound`
  (certainly skipped: a gate or parse only moves a detector between its
  refine and search cadences) released, and the ones `predictDueTimes` and
  `nextDueCandidates` expect next read back and normalized ahead. The decode
  worker is told that lower bound (`floor`) and closes the samples before it
  itself, sending bare timestamps — and on AV1 never decodes a sample before
  it whose unit refreshes no reference slot (`core/av1-refs.ts`: such a unit
  leaves the decoder as it found it). It is also handed the scheduler's
  check plan (`core/detectors/check-plan.ts`): each detector is checked at
  the first sample its interval has elapsed by, and its interval is one of
  its few cadences, so where its next checks can land branches over the
  stream's real timestamps; such units no branch reaches go undecoded too
  (~30% fewer decodes on a 1080p60 AV1 scan; non-reference frames are cheap
  to decode, so the scan itself gains a few percent). When the scheduler
  reports calm (no gate pass for a quiet period, no open match), the worker
  skims keyframe-to-keyframe (hop capped at 2.5s so short screens can't
  hide), snapping back to dense decode on any gate pass. Dense and skim stretches
  read one decode stream per slice (`worker/frame-source.ts`): a hop `seek`s
  it to the sample `getSample` would return, decoding forward from where it
  stands or jumping to the hop's keyframe when that lies ahead, rather than
  starting a decoder at the keyframe for every hop. The seek fallback drives
  one worker and widens its stride over calm footage the same way; its
  metadata wait is bounded so an undecodable file errors instead of hanging.
  A scan is all or nothing: leaving the page cancels it and nothing is saved.
  The hardware decoder caps a scan: Chromium serializes every hardware
  decode of the page on one GPU-process thread (an M5 Pro decodes 1080p60
  AV1 at ~2,700 frames a second, ~45× realtime, however many lanes share
  it), and the slices' software decoders cost more CPU than they add.
- VoD frame readback (`worker/readback.ts`): the 2D canvas readback is the
  reference, but every canvas readback of a hardware frame is also served
  one at a time on the GPU process's main thread, which the decoder needs
  too. Where it reads the same pixels (`worker/readback-parity.ts` compares
  one frame per slice) a scan reads through WebGPU instead. The hardware
  frame itself `copyExternalImageToTexture` converts differently, but an
  `ImageBitmap` of it is converted on the GPU exactly as the canvas converts
  it; failing parity, the frame's planes copied out to a CPU frame are too
  (two readbacks and an upload on the GPU process's main thread, ~45% of
  its time on a 720p scan). Either is copied in and mapped back
  asynchronously.
  In the same submission the GPU upscales a sub-1080p picture
  (`worker/cubic-upscaler.ts`, assuming no bars; a picture with bars takes a
  second trip) and converts the canonical picture to gray
  (`worker/gpu-gray.ts`, bit-identical to `frameGray`), so the analyzer
  starts its gates with neither left to do.

- Field scores (`core/field-scores.ts`): an event carries no overall
  confidence but `scores`, 0..1 per field of `data` its read vouches for,
  keyed by the field's path (`players.3.name`, `stage`; fields read as one
  unit share a key naming each, `mode,stage`, and are never taken from
  different reads). They are rounded to four decimals where the event is
  made, so a store, a tape and a scan log hold the same numbers. Three jobs
  that one mean used to do are separate:
  - **Floor.** The timeline drops a read whose scores average under the
    kind's `minMeanScore` (default 0.6): it is not a read of the screen at
    all. A read scoring no field is dropped too, which is how a detector
    says a cross-check failed (an X Battle card mid-animation).
  - **Vote.** Reads of one run (same type, merge window, content guard) are
    one kept read whose every scored field takes the value its reads back
    with the most score in total; an unread value (null, empty) casts no
    vote. A name one frame misread is outvoted by the frames that read it,
    whatever else those frames got wrong. `t`, the frame and the unscored
    data are the read's that agrees with the outcome on the most fields
    (the earliest on a tie). A read that changes no field's value is merged
    (reported as no change) unless it completes the kept read; one that
    changes values under the same base is `amended`. Kinds with `progress`
    (X Battle cards) vote only among reads level on the animation, and
    `first` / `every` kinds not at all.
  - **Stop.** A kind's `complete` says when a read holds everything its
    screen shows, each field as well as a clean frame reads it; the scheduler
    stops parsing the screen once the kept read is complete (`isComplete` in
    `core/events.ts`). The floors in those invariants sit just under the
    lowest clean fixture read of their field. A board: every row's weapon,
    name (0.6), paint (0.6) and stats (0.75), the header and both scores
    (none on a no-contest); personal results: header, weapon and all twelve
    badges; death: weapon, name (0.7) and every badge (0.65); intro: mode
    and stage (0.7); minimap: every live card's name (0.7), on the spectator
    screen also every card whole. Kinds without `complete` (the counter, the
    kill feed, the X Battle cards) never stop on a read. A name's score does
    not catch a glyph twin (a "p" read as "P" scores 0.92), and a field that
    never reads (a streamer's overlay over it, a name of unknown glyphs)
    costs the stagnation fallback on every showing of its screen.
  The events CSV lists a read's `mean_score` and whether it is `complete`.
  Every fixture of a kind that declares a complete read must come out
  complete in its suite (`assertCompleteness`), unless its `expected.json`
  says `options.incomplete`: a frame caught mid-animation, or a screen with a
  field that never reads; `tests/logic/complete-reads.test.ts` holds each
  kind's read one field short.
- A screen that holds still is read one frame at a time, never as a stack of
  its frames. A per-pixel median of the last five frames was measured
  (2026-11-13: 41 results screens, 9 replay browser entries, 13 X Battle
  cards and 37 intros of eight VoDs, 360p to 1080p60, H.264 / VP9 / AV1 at
  1.7-17 Mbps) and left out. The timeline kept the same read on 99 of the
  100 screens (the other differs by a dot twin) and reached a complete read
  after the same number of parses on all but one, a parse later stacked.
  Why it has nothing to remove: an encoder carries a still block over
  from the frame before instead of coding it again, so a settled screen's
  noise stands as still as its text (frames differ by ~0.2 gray levels on
  average, the mean field score of a results screen's reads by under
  0.002). What does change between
  frames is the entry animation and the half second an encoder takes to
  sharpen a screen after a cut, where a stack only lags behind the newest
  frame; those reads are already dropped by the floor or outvoted per field.
  The scheduler also stops at the first complete read, the first or second
  parse of most results screens, before there is anything to stack. And a
  stack brings misreads no single frame has: names swapped in place (X
  Battle aliases turning into the real names in the battle log) blend into
  glyphs neither frame shows, unless stillness is judged per text ROI. Only
  the intro's stage line, drawn over moving gameplay, read better stacked
  (+0.01 mean score), without changing a value the timeline kept.
- A VoD scan writes a log of every frame it analyzed (`core/scan-log.ts`,
  per lane: which detectors were due, each gate's verdict, whether the parse
  ran and what it read), saved with the VoD (`vod-scan-logs`) and put into
  its games' Game data zips. `scan-vod --replay` runs the scan again from it,
  see "Scan log and replay".
- Gates and parses read the frame's gray/RGB/HSV
  through `frameGray`/`frameRgb`/`frameHsv` (`core/image.ts`), converted once
  per frame and shared: never delete or write them, and never pass them a
  derived mat. Gray and RGB come from WebAssembly SIMD kernels
  (`core/frame-kernels.c`) bit-identical to `cvtColor` (tested on every
  24-bit color) at under half its cost. A gate probing a few small ROIs of a
  rectified region uses `createProbeWarp`, which replays OpenCV's f32
  bilinear warp at those pixels only (exact; `tests/frame-kernels.test.ts`).

## WebGPU

Template matching (every `TM_CCOEFF_NORMED` the recognizers run) and the
sub-1080p frame upscale can run on the GPU; every other step stays on the CPU.
The GPU is an accelerator only: the same algorithms make the same decisions.

- **Match steps** (`core/match-steps.ts`): recognizers are generators that
  yield every match their next decision needs (`MatchRequest`: an image,
  templates, a placement window per template, optionally a content `key`) and
  resume with the max scores. `runSync` answers lazily on the calling thread
  and is what `Detector.parse` runs; `all` steps generators in lockstep so
  independent reads share a round trip. Every detector implements
  `parseSteps`; within a parse, reads are lockstepped wherever the sequential
  code's consumption order, memo reads/writes (death tag, kill rows: the kill
  parse predicts its memo misses on a copy of the memo and reads only those
  ahead) and detector state stay exactly as before. `speculative`
  additionally prefetches merge / recut candidate sets in lockstep (batching
  drivers only; on the CPU it is wasted work).
- **Exact scores on both drivers**: a score is TM_CCOEFF_NORMED computed
  exactly — integer cross, window and square sums, one f64 normalization with
  OpenCV's guards (`normalizeNcc`), f32 result — so the CPU and the GPU give
  bit-identical scores and the same events. OpenCV's own `matchTemplate` (the
  pre-migration CPU path) runs a float DFT that wanders up to ~3e-4 from the
  exact score: never a decision on the fixtures or the VoD test slices, but
  enough to reorder a near-tie (seen once in a browser scan: an 8th-ranked
  strip-weapon candidate, scores 7e-7 apart), hence exact on both. On the CPU
  the cross sums run in WebAssembly SIMD (`core/cross-sums.c`, compiled into
  `cross-sums.ts`; regeneration steps in the C file), large jobs as one f64
  `filter2D` (rounded: exact), and the window sums come from integral
  images — faster than the `matchTemplate` path it replaced.
- **Frame pass** (`core/detectors/frame-pass.ts`): the worker and the CLI gate
  every due detector in registry order, then run all approved parses — one
  lockstep of their steps on the GPU — and record results in registry order.
  Scheduler decisions within a frame depend only on each detector's own
  state, so this equals gating and parsing one detector at a time.
- **Matcher** (`worker/gpu-matcher.ts`): each step is one submit of three
  passes — per-image integral images (window sums), a score pass (one thread
  per 4 vertically adjacent placements; cross sums as packed u8 dot products;
  an f32 estimate folded into the job's max) and a select pass returning the
  exact 64-bit integer sums of the placements within `EPS` of that max. The
  CPU finishes those with `normalizeNcc` — the exact score, identical on
  every GPU and to `runSync`'s. More than `K` near-tied placements, or a
  request the kernel cannot take, are finished on the CPU with the same exact
  arithmetic. Scores are cached per run by (`key`, template, window) — the
  window is part of a score's identity.
- **Frame upscale** (`worker/gpu-frame-scaler.ts`, kernel in
  `worker/cubic-upscaler.ts`): `normalizeFrame`'s INTER_CUBIC upscale of
  sub-1080p pictures (13-25 ms of WASM per 720p frame) as an integer kernel
  reproducing OpenCV's 8-bit cubic resize bit for bit; 1080p copies and
  INTER_AREA downscales stay on the CPU. A VoD scan reading back through
  WebGPU runs the same kernel in its readback worker instead (see "VoD frame
  readback"). Importing a hardware-decoded VideoFrame as a GPU texture
  converts its YUV differently from the 2D canvas; a CPU copy of its planes
  converts the same.
- **Worker** (`worker/analyzer.worker.ts`): creates the matcher (and scaler on
  its device) at init when enabled and an adapter exists; a failed creation
  or a device lost mid-run (`device.lost`, or a failed readback) hands the
  pending step to `runSync`, so the generators still run exactly once and no
  event is dropped or duplicated, and later frames stay on the CPU. A device
  whose submit → `mapAsync` round trip is slow (`hasFastReadback`; Firefox
  resolves GPU promises on a ~100 ms timer, Chrome in ~0.2 ms) is dropped at
  init: every step and upscale waits on one, so there the CPU is far faster.
- **Node** (`node/webgpu.ts`): scripts get WebGPU from Dawn, the `webgpu` npm
  package — deliberately not a dependency: `npm i webgpu` anywhere and point
  `WEBGPU_NODE` at its package dir. `scanner:scan-vod --gpu` scans on it
  (the CSV must stay byte-identical to a CPU scan), `--record <dir>` writes a
  replay corpus (`scripts/scanner/match-corpus.ts`), `scanner:gpu-replay`
  times it and checks every score against an exact JS reference and, with
  `--cpu`, against `runSync` (0 mismatches is the bar for any kernel change),
  and `scanner:gpu-parity` requires byte-identical events from both paths on
  every fixture.

## Glyph cells

A glyph template is a line-height cell: its ink box plus the row the
baseline of its line crosses it at (`baseline` in the atlas meta, fractional,
from the top of the box; past the box for a glyph floating over the baseline).
The box is stored tight, so the cell costs no pixels. Shapes that differ in
nothing but height are separate templates this way: 'p'/'P', 'c'/'C',
'_'/'-'/'¯', '.'/'・', ','/"'", '°'/'。', a kana and its small form.

- **Atlas**: a font glyph's baseline is the font's own (`measureText`'s
  `alphabeticBaseline`). A fixture crop is cut from a labeled line, so
  `scanner:bootstrap-atlas` writes which line and at what row (`line`), and
  `scanner:build-glyph-atlas` places the line's baseline from the font: each
  crop's ink bottom less how far under the baseline the font draws that
  character, the median over the line (a line of kana has no flat capital to
  read it off). A crop keeps the height it was drawn at, even where the font
  disagrees (the robot fixture's '・' on the baseline).
- **Finding the line** (`lineFrame` in `core/glyphs.ts`): the segments are
  first read with the templates sliding freely, as before. Each of a
  segment's best candidates says where the baseline would be if the segment
  were that glyph (the row its template matched best on plus its ascent,
  asked of the matcher, not read off the ink box: a border line in the crop
  or a neighbor's overhang stretches the box). The baseline that keeps the
  most score over the line wins, so twins at two heights are settled by the
  glyphs beside them. The glyphs on it then give the line's scale (segment
  height over template height, the median of the tall ones: panels rectified
  to the scoreboard layout come out up to a tenth off their set's size) and
  its tilt (the median slope over all pairs: exactly zero for a level line,
  about one degree for battle log tags and what levelling leaves in a death
  tag).
- **Reading in cells**: every segment is then read again with each template
  kept to its cell: it may only sit between flush with the cell's top and
  flush with its bottom, give or take a row (`cellTolerance`), and it pays
  for the share of the segment's ink its cell leaves out
  (`CELL_UNCOVERED_WEIGHT`: the tail of a 'j' is all that tells it from an
  'i'). Ink outside the line's own rows (the tallest and deepest glyph of
  the set around the baseline) is not counted as the segment's at all. The
  merge, re-cut and re-segmentation passes all read in cells. A line where
  nothing was read keeps the free read.
- **What it replaced**: `names.ts` no longer measures baselines. Gone are the
  underscore, dot, ring, cap line, descender and 'P'/'p' resolvers and the
  raised-mark rule of the stroke merge. What is left there decides shapes at
  one height ('b'/'h', 'D'/'O', 'r'/'T', 'u'/'Y', 'S'/'B', a blurred '!') and
  detached marks a soft capture thins (accents, (han)dakuten: the cell's
  uncovered ink reads most of them, but a minimap name still loses its ぎ
  without the probe), and context ('I'/'l'/'1', 'O'/'0', '-'/'ー', a period
  between Latin letters, 'º' as '°').
- **Scores**: a glyph at its own height scores about what it did sliding
  freely (its height penalty is now taken against the line's scale, the
  segment's ink counted within the line's rows only); a glyph off its
  height scores less or is not read at all. The floors and margins around
  the recognizer were left where they were.
- `tests/glyph-cells.test.ts` draws its own font and line (twins at both
  heights, a tilted line, a line off its set's size, a border line in the
  crop); it needs OpenCV but no fixtures.

## Threshold margins

The detectors hold a few hundred tuning constants, each attested only by the
fixtures that happened to exist when it was set. Where a detector compares a
measured value (a gate probe's brightness, a match score, a score margin
between twins, a pixel share) to such a constant, it does so through
`core/decisions.ts`: `Decisions.atLeast(id, value, threshold)` and its
siblings `above`, `atMost`, `below` are the plain comparison, plus a record of
it when a recorder is set. The id is `<file under core/>:<CONSTANT>`
(`death:GATE_DARK_MAX_MEAN`, `scoreboard/names:BH_SCORE_MARGIN`), with a
`#site` suffix when one constant decides more than one thing.

`pnpm scanner:report` ends with the audit (`scripts/scanner/threshold-margins.ts`):
every detector runs over every fixture, cross-detector negatives included, and
each threshold is printed with the fixture value nearest to it on the passing
side (the comparison held) and on the failing side, sorted by the smaller of
the two margins as a share of the span the observed values cover. The ranking
counts a detector's decisions on the fixtures of its own screen; what it
measured on the other detectors' fixtures is listed beside them as "other
screens", and thresholds only those reach come last. `pnpm scanner:report
--margins` prints the audit alone.

- A margin near zero means one fixture sits on the threshold: the next
  encode of the same screen can land on the other side. Before moving such a
  constant, look at what is nearest: one probe of several that are counted
  flips nothing on its own, and a floor cut through thousands of per-glyph
  scores always has a fixture on it (moving it only moves which one).
- "never on any fixture" means the threshold is attested from one side only:
  nothing shows where it stops being safe.
- Decisions short-circuit as in production, so a later condition is recorded
  only for reads that passed the earlier ones.
- New threshold comparisons go through `Decisions`; per-pixel classification
  loops and the glyph prescreen stay plain comparisons (too hot, and a single
  pixel decides nothing).

## Scan log and replay

What a scan reads does not follow from the footage alone. Which frames it
looks at and in what state it reads them depends on how it ran: a VoD is
split into one lane per worker (their number follows the machine's cores),
each lane starts with a scheduler, a timeline and detectors of its own, calm
stretches are skimmed, and frames come at the file's own timestamps. The
detectors carry state from frame to frame (the death and kill-feed memos, the
player-status strip's sticky fit, the strip-weapon sampling counter) and the
scheduler decides from what earlier frames showed. `scan-vod` on the same file
runs one lane on ffmpeg's 8 fps grid, so it need not read what the browser
read: on a 150 s Rainmaker slice, 111 of the browser scan's 189 events had no
identical counterpart in a plain `scan-vod` run.

So a VoD scan keeps a log (`core/scan-log.ts`): per lane, every analyzed
frame's timestamp and, for each detector that was due, the gate's verdict and
variant, whether the parse ran, and the type and field scores of each event
it read. It is built on the page from the worker's `result` messages
(`vod-scan.ts`), saved with the VoD (`vod-scan-logs`) and put into every Game
data zip of that VoD as `scan-log.json` (the whole scan's, not just the
game's: a detector's state starts at its lane's start). The log is its own
JSON form, three bit masks per frame over a table of detector ids, around
30 bytes per frame plus the scores of the reads it holds (some 4 frames a
second while the scan is not skimming).

`pnpm scanner:scan-vod <video> --replay <scan-log.json>` runs that scan again
(`core/detectors/replay-pass.ts`):

- Each lane gets detectors and a timeline of its own and is shown the frames
  it analyzed, in its order. ffmpeg decodes the video at its own size and
  timestamps; a logged frame is the frame at that timestamp (or, for another
  encode or a scan that read by seeking, the last frame before it, which the
  summary says).
- No scheduler runs. The logged detectors are due, a gate takes the logged
  verdict, a parse runs where it ran, and a parse that reads the logged event
  types, each scoring as many fields, takes their logged scores, so the
  timeline keeps the reads the scan's kept and votes their fields as it did.
  Only the events' `data` comes from the replay's own pixels.
- The lanes are stitched and finished as the page does it
  (`stitchLanes`, `withoutInvalidObjectives`), so the CSV is the one the VoD's
  `Raw detections` export gives.
- Every gate the replay's pixels decide differently and every parse that
  reads other events, or the same ones with a field score more than 0.02
  off, is printed; the summary counts them. ffmpeg decodes the same frames as
  the browser but converts them to RGB a little differently, so scores
  drift by a few thousandths while the reads stay the same. On the Rainmaker
  slice (VP9, four lanes, scanned in Chromium, measured when a read still
  had one confidence): all 600 frames found at their timestamps, all 7,051
  gate checks as logged, 165 of 166 parses within 0.02, and an events CSV
  identical to the browser's.
- `--start T --duration S` pick the stretch to reproduce: each lane reaching
  into it is replayed from the lane's start, where its detectors' state began.

It needs the file the scan read (same frames at the same timestamps). A
replay on changed detector code shows what the scan would have read with it:
the frames, the lanes and the order stay the scan's, so a fix can be checked
against the scan that showed the misread. Live captures keep no log: there is
no footage to replay it on. `pnpm scanner:replay` is the older tool for a
folder of extracted frames, run through a scheduler of its own.

State a detector keeps between frames is reproduced as long as it lives in
the detector instance and follows from the frames it was shown. State kept
anywhere else, or a decision that depends on something the log does not hold,
has to be added to the log (bump its `VERSION`).

## Event tapes

A tape (`tests/tape.ts`) is a real event stream as a `TimelineBuilder` held
it: `tests/tapes/<name>.tape.jsonl`, a header line (`description`: the builder
situations the footage holds, `source`: what it was recorded from) and then
one event per line, fractions rounded to four decimals. No images, so tapes
test everything downstream of the detectors on real footage in the `unit`
project.

`tests/logic/match-builder-tapes.test.ts` builds every tape and compares the
result to its golden file `tests/tapes/<name>.matches.json`: each match with
the tape lines it was built from (`sources`, as index ranges), its flags
(`unbacked`, `historyOnly`, `ingestSkipReason`) and the whole `ScannerMatch`.
It also checks that a cached rebuild of the growing timeline equals a fresh
build. **A golden file is what the builder does today, not ground truth**: a
known-wrong split stays in it until the builder is fixed, and then shows up as
a diff to read.

- Record from a video: `pnpm scanner:scan-vod <video> --start T --duration S
  --tape <name> --description "<situations>"`. A slice that starts mid-game or
  stops before the results is how a missed intro or results screen is taped.
- Record from Game data zips: `pnpm scanner:tape <name> "<description>"
  <zip>...` (validated like `scanner:unpack-zip`). A zip holds one match's
  source events, so several zips of one session make a session tape, minus
  the events no match claimed.
- Running the test writes a new tape's golden file. After a builder change
  that is meant to move the output, rerun it with `-u` and review the diff.
- A detector change does not touch the tapes: they keep the events as they
  were read back then. A changed event shape does not either: the header's
  `events` is the event version the tape was recorded at (absent = 1) and
  `Tape.parse` upgrades the events through `core/event-version.ts`.

## Fixtures

A test case is a directory `tests/fixtures/<detector>/<case-name>/` with
`frame.png|webp|jpg` (raw capture, never lossily re-encoded) and `expected.json` (partial
expectations, sendou ids; `stageLabel`/`weaponLabel` are informational for
the human corrector — tests compare only ids). A frame that already serves
another detector's fixture (a kill feed caught in an objective frame) is
symlinked (`ln -s ../../objective/<case>/frame.png frame.png`), not copied,
and the kill suite's cross-negative sweep skips shared frames by real path.
Negative cases
(`{ "event": "none" }`) go in the shared `tests/fixtures/negative/`; every
detector's suite sweeps them. Every live misread should become a fixture —
an expanded match card's `Game data` zip holds each analyzed frame
(lossless WebP, pixel-exact) with a prefilled `expected.json` in a folder
that drops into `tests/fixtures/<detector>/` as is. A zip sent in by a user is
untrusted: unpack it only with `pnpm scanner:unpack-zip`
(`node/game-data-zip.ts`), which accepts nothing but that exact shape — the
`scanner-misread` Claude skill drives the zip → fixtures → fix loop. **Fixture ground-truth labels are
hand-corrected by the user (the Splatoon domain authority) — treat them as
definitive over any matcher output.** Fixtures are committed as plain blobs
(no LFS for now); keep additions deliberate — fixture IO is isolated in
`node/fixtures.ts` if a retreat to LFS/an external corpus is needed.

## Tower Control / Rainmaker track

Both modes draw one overlay (`core/detectors/objective/track.ts`, geometry in
`rois.ts`): a dotted track under the icon strip, ends x514..1405 at y155,
with the objective's icon riding it and a "Remaining" plate per team hanging
under the furthest point that team pushed to — so a team's plate always sits
on the half it pushes into, and the left team pushes right. The gate tells the
track from the SZ plates by the dots, which sit at a fixed pitch and phase in
every lobby (a comb projected at that phase, per window, with the two
worst windows dropped so a marker or backdrop edge can't sink it). The icon is scored

## X Battle cards

After an X Battle game the lobby shows one near-black card
(`core/detectors/x-rank/`, geometry in `rois.ts`): `XSetCount` ("WINS
LOSSES 1 - 2" over win slots and loss squids) after every game that leaves
the set undecided, then after the deciding game `XSetResult` (the "2 - 3"
header, one VICTORY/DEFEAT tile per game in play order, X Power and its
signed change) followed by `XRankPosition` ("#259" and an up/down arrow, or a
flat one when the position held).
Every card carries the mode off its icon (`img/modes/*`, RGB templates on
black). The Anarchy Series card after a series game draws the count card's
layout too, but with five win slots: ink where only it has slots fails the
count gate (`negative/anarchy-series-card-*`). Numbers are BlitzBold, read with the team-digit atlas rescaled;
punctuation ("." "-" "+") is told apart by ink-run geometry since the digit
templates can't match anything smaller than themselves.

All three animate toward their final value and hold it only briefly: the
count card opens on the score before the game, fills the new slot and only
then flips the digits (~0.5s before fading); the set result counts the old
X Power to the new one in ~0.3s; the position counts in the arrow's
direction. So no card kind declares a `complete` read (the first clean read
is the stale one), each gate returns a `signature` over its numbers, and the
timeline orders same-type reads by the kind's `progress` before any vote:
a further-along read replaces the kept one, an earlier one
merges into it. The count's end can fall between two sampled frames (a 2 fps
live capture), so a set result read after the change lands takes its power
from the power before it plus the change whenever an earlier read showed the
old value (the kind's `carryOver`); the old value holds ~1.5s, the final one ~1s. A count read whose digits disagree with its slots, or a set
result whose header doesn't describe a decided set of tiles (tiles still
popping in), scores no field, so the timeline drops it. The result tiles center on
the card (five games three over two, four two over two, three in one row
midway between), so each row is found as a band of VICTORY yellow / DEFEAT
purple text and each tile as a run of its columns rather than at a fixed
slot. A gain shows "+30.0" on a teal splat and an orange up arrow, a loss
"-29.2" on a grey splat and a grey down arrow, a held position a green
right arrow (`SAME`). The arrow follows the number, so it is read as the
card's rightmost ink. The Japanese cards say WIN/LOSE on the tiles and
